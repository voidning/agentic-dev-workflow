# AI 工程协作

`agentic-dev-workflow` 是一套面向 AI Agent 的工程协作 Skill，适用于代码、Skill、可复用提示词、Agent 配置和自动化流程的开发与修改。

它把任务组织成一个有证据的工作闭环：用户确定目标与关键取舍，主 Agent 协调推进，实现者完成修改与自检，高风险、跨模块复杂改动、反复失败或用户明确要求时，再由独立子 Agent 按原始需求验收。每次交付都应能回答：做了什么、怎样证明、还有什么未确认。

本 README 面向使用者，解释设计原理与使用方式。执行规则以 [SKILL.md](SKILL.md) 为准，具体委派模板和检查方法见 [独立验收协议](references/verification.md)。

## 使用方法

在支持本 Skill 的 Agent 环境中，可以明确调用：

```text
用 $agentic-dev-workflow 修复这个问题：……
```

```text
用 $agentic-dev-workflow 创建一个 Skill，用来……
```

```text
用 $agentic-dev-workflow 调整这个自动化流程。
目标是……，必须保留……，完成后应能验证……。
```

尽量给出目标、相关项目或材料、重要约束，以及你对完成结果的期待。主 Agent 负责查找已有信息、补全可检查的标准，并集中提出必要问题。

仅要求审查、探索或规划时，流程停在对应阶段。普通知识问答和文案润色不需要启动整套协作。做特定类型的成果时，本 Skill 与对应制作能力配合，例如创建 Skill 时使用 `skill-creator`。

## 原理一：把目标变成可以判断的结果

“优化一下”和“已经完成”之间，需要明确的验收条件。开始修改前，先约定四件事：

- **目标行为**：在什么条件下，应观察到什么结果。
- **保留行为**：哪些现有能力或约束必须继续成立。
- **验证方法**：用实际操作、测试、日志、截图或测量确认。
- **阻断条件**：什么问题未解决就不能宣称交付通过。

例如，“让设置保存可靠”可以落实为：修改后重启仍保留设置，无效输入得到明确处理，旧配置继续可读。这种标准同时给实现者和验收者提供依据。

标准可以因真实需求变化而调整，但必须说明理由。不能在看到结果后，悄悄降低标准让实现通过。

## 原理二：实现自检与独立验收分工

| 角色 | 主要责任 |
| --- | --- |
| 用户 | 确定目标、优先级与关键取舍，判断审美、手感等主观体验 |
| 主 Agent | 管理范围与进度，分配工作，核实分歧和证据，负责最终交付陈述 |
| 实现者 | 调查、修改、自检，提供实际运行结果与已知限制 |
| 独立验收者 | 在新上下文中按原始需求检查成果，独立重跑关键验证并报告问题 |

小任务由主 Agent 实现并针对性自检，不默认启动子 Agent。复杂任务可以分离实现角色；只有能独立推进的工作才并行。

新上下文有助于减少验收者沿用实现者假设的机会，但不保证判断一定正确。验收者需要拿到简短中立任务包（目标、必要背景、允许范围、验证方式、停止条件），按需包含：原始需求、确认的取舍、验收条件、目标版本、运行入口和已知基线。实现者的“已经解决”只能作为待核实陈述。

验收者不修改被验收成果、既有测试或验收标准。发现问题后交回实现者修复，再复验新版本。主 Agent 核实关键证据，避免把多一个 Agent 的赞同当作质量保证。

## 原理三：让证据形成反馈循环

```text
需求 → 调查与基线 → 方案与验收标准 → 分批实现与自检
                                      ↓
                           按风险决定独立验收或直接交付
                             ┌────────┼────────┐
                            通过     退回      受阻
                             ↓        ↓         ↓
                            交付   修复后复验  说明缺口
                             ↓
                       按需保留必要接续信息
```

基线用于区分原有问题和新增回归；修复前后的同条件对照用于判断问题是否解决。验收必须对应最终版本，相关文件或运行配置变化后，旧验收可能失效。

三种结论的含义是：

- **通过**：必要验收项有证据支持，没有阻断问题。
- **退回**：确认存在本次需求遗漏、缺陷或回归。
- **受阻**：缺少必要环境、权限、工具或数据，无法完成判断。

受阻时可以交付已完成的部分，但必须标明待验收范围。“没有发现问题”只说明实际检查的范围。

## 原理四：不同成果使用不同证据

| 成果 | 验证重点 |
| --- | --- |
| 代码 | 正常输入、关键边界、错误路径、状态结果与相关回归 |
| 界面 | 实际渲染和操作，对照认可的样板与交互目标 |
| Skill、提示词 | 文件有效性、规则一致性，以及实际任务中的触发和执行行为 |
| Agent 配置 | 实际加载值、覆盖关系、工具边界与隔离任务表现 |
| 自动化 | 隔离试运行中的触发、输出、失败处理、重试和重复执行 |

对于 Skill 和提示词，验证分为三层：

1. **文件验证**：格式、元数据、引用和脚本入口是否有效。
2. **规则审查**：有没有冲突、过度限制、范围扩张或不可执行要求。
3. **行为验证**：让新上下文的 Agent 使用候选成果完成任务，检查实际操作与结果。

行为案例按影响选择：应触发的正向任务、不适用的反向任务、工具缺失等异常，以及原有能力的回归。测试自动触发时，不应先明确命令 Agent 必须使用该 Skill，否则测到的只是显式调用。

格式通过、文件已安装、运行环境已加载、实际行为正确，是四种不同结论。模拟场景与干跑也只证明其覆盖的条件，不能冒充真实端到端结果。

## 原理五：工作量随风险调整

小改动只需简短标准和针对性自检；普通任务增加边界与路径检查；跨模块复杂改动、高风险、反复失败或用户明确要求时安排独立验收，按需增加计划、隔离和恢复验证。基线与标准可以记录在上下文，不强制生成文档。

先定位再读相关片段，已读未变内容不重复读取，日志与浏览器状态只保留相关证据。子 Agent 默认新上下文与短任务包，只有确实依赖历史时才继承完整上下文，独立验收仍保持新上下文。实现稳定并自检后再集中验收。必要检查通过后，只有新改动、失败或未解决风险才触发进一步验证，修复只复核受影响内容。用户明确要求的验证不能省略。范围完成、检查通过且限制说明清楚后即交付，不额外扩建系统、文档或审查轮次。

一次修复无效后，先保留证据并重新判断原因，确定有边界的下一步。按已有自主授权和项目规则决定是否继续；自主授权内常规修复不逐次求批；核心重构、破坏性操作或明显扩大范围先提交具体方案。不能不断叠加猜测性补丁、换评审者寻求通过，或放宽测试来结束任务。

## 原理六：经验沉淀到工具与项目中

长期只维护必要的项目规则、任务记录与执行证据。重复且可判定的问题，优先变成测试、类型检查、依赖约束或可靠的标准实现。需要判断的问题，再保留为简短工作指导。

评价流程的指标包括完成总耗时、用户介入次数、交付后回归、重复错误和验收误报。目标是减少返工与人工补步骤；Agent 数量、代码量和报告长度不能代表质量。

修改协作 Skill 自身时，应先固定本轮标准并保留可对照的原版本，不强制新建文档。低风险修改可用文件检查与代表性任务的规则推演；高风险、反复失败或明确要求时再进行实际行为评测。推演不能证明实际执行，也不能证明节省比例。候选 Skill 是被测对象，不能通过重写自己的通过条件来证明自己有效，也不应无限递归地为验收者再开验收者。

## 能力与限制

这份 Skill 是工作指导，不是内置调度器、自动测试平台或强制审批系统。它不会自行提供子 Agent、浏览器、测试环境或 CI；这些能力需要由实际运行环境提供。

子 Agent 不可用或被禁止时，主 Agent 可以继续完成授权内的实现和自检，若本次需要独立验收，必须说明未执行及待验收范围；轻量任务可凭相关自检交付。用主 Agent 切换角色口吻不算独立验收，也不能通过创建其他用户任务来绕过限制。

模型可能共享盲点，运行结果也可能有随机性。独立验收需要可重复的证据和适量行为评测支撑，不能保证发现所有问题。审美、手感、产品价值仍需要人的判断。

强制约束应由隔离环境、测试工具链或自动检查承担。发布、真实调度、通知、外部写入等动作遵循已有授权，Skill 不扩大操作权限。
